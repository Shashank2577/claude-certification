Host page everything you can add, and where it goes

Adding something to this repo, without remembering where.

Two commands cover most of the work. Everything else is a table, a checklist, or a loop. Nothing on this page is aspirational: every path, flag, JSON key and validator message here is copied out of the repository, and every count was computed from it.

One command

Add a new exam.

Every certification is a JSON object in content/certs.json with a folder of content hanging off its id. This command creates all of it, plus the three study plans and a placeholder candidate report, from the files in templates/.

run from the repo root 
pnpm scaffold:exam --id=cca-security --role="Security" --tier="Professional" \
  --domains="Threat Modelling,RAG Security"

The flags, all five

--id=<kebab-case>required
Must match /^[a-z][a-z0-9-]*$/ or the script exits. It becomes the certId in every path it writes, and its first two characters become the id prefix in the generated question and lesson ids.
--role="..."default "Something"
Substituted into the cert name as Claude Certified {{role}} – {{tier}}.
--tier="..."default "Foundations"
The other half of the cert name.
--domains="A,B,C"required
Comma-separated domain names. Each becomes d1-slug, d2-slug and so on, with two task statements numbered 1.1 and 1.2. Weights are split evenly and the remainder is added to the first domain so they sum to exactly 100.
--forceoptional
Overwrite per-domain files that already exist. Without it the script prints kept <path> (exists) and leaves them alone. Re-running is safe either way.

What this creates

  • content/certs.json — the cert, its domains, task statements and a scenario stub.
  • content/modules/{certId}/{domainId}.json — one lesson skeleton per domain.
  • content/questions/{certId}/{domainId}.part-1.json — a first batch of two worked examples.
  • content/flashcards/{certId}/{domainId}.json — one card per domain.
  • content/study-plans.json — 3-day, 7-day and 14-day plans appended.
  • content/insights.json — a placeholder candidateReports[] entry.
  • content/resources.json — nothing. It writes no resources on purpose; add them as you write the lessons.

What it cannot do for you

  • src/components/visuals/registry.ts. Any visualId your lessons reference has to exist there or the linter fails the lesson.
  • docs/index.html. The marketing card, the counts in the stats strip, and the CERTS and ROLES arrays are a separate structure it will not touch.
  • Your task statements. They arrive as TODO: first objective for …. Every question keys to them, so fix them first.
  • Lesson prose. Every eli5 and body is a placeholder. eli5 is the first thing a reader sees.
  • Judging whether your domains match a real exam guide. It has no idea what the official weights are.
  • Validating anything. It exits 0 having written files. pnpm validate:content is the gate, and you run it yourself.

The two-structures trap

A certification lives in two structures that share no code. content/ is what the app reads and what the linter checks. docs/index.html is hand-written marketing: an <article class="exam"> in .exam-grid, five or seven .stat numbers in the strip, and entries in the CERTS and ROLES arrays at the foot of the file.

The scaffolder writes the first and never touches the second. Nothing in this repository validates the second. An exam can be completely, provably valid in content/ and entirely absent from the landing page, and pnpm validate:content will still print All content checks passed.

One command

Add a new interactive explainer.

An explainer is a self-contained React client component plus one key in the visual registry. The command writes the file, names the component, and inserts the registry entry for you.

run from the repo root 
pnpm scaffold:visual cca-rag-security "RAG security" "Where retrieval meets access control"

What this creates

  • src/components/visuals/cca-rag-security.tsx, with MyVisual renamed to CcaRagSecurity and the caption filled in.
  • A new key in VISUALS in registry.ts, inserted immediately before the closing brace, with the title, description and a dynamic import() loader.
  • The full eight-rule checklist as a comment block at the top of the file.

What it cannot do for you

  • The diagram. You replace the STEPS array and the whole <svg>. There is nothing generic to fill in.
  • Reference it from a lesson. Add "visualId": "cca-rag-security" to the lesson by hand.
  • Prove the text fits. That is rule one, and it is the one the generated file cannot check.

The id must be kebab-case. If the .tsx already exists the script stops and tells you to pick another id; if the id is already registered it prints kept registry.ts and leaves that file alone. It then prints its own next-steps, including the exact typecheck and lint commands for the file it just wrote.

Reference

Every entity, its template, its path, and what catches a mistake.

Six of the seven render from a file in templates/, so the template and the scaffolder cannot drift apart. Where a validator message is quoted in the third row of a card, it is the literal string scripts/validate-content.ts prints, so you can match it against what you see on the terminal.

  1. ENTITY 01

    Certification

    Template
    templates/cert.json.template
    Lands in
    content/certs.json — one object in the top-level array. Keys: id, name, tagline, description, examInfo, domains, scenarios.
    Validator catches
    Missing name or tagline, an empty domains array, malformed JSON, and an empty certs.json. It does not check that domain weights sum to 100.
  2. ENTITY 02

    Domain

    Template
    templates/domain.json.template
    Lands in
    content/certs.json — one entry in that cert's domains[]. Ids are d1-slug, d2-slug. Task statements are <domainNumber>.<index>.
    Validator catches
    unknown taskStatementId from any lesson or question that references an id the domain does not define, and task statement 1.3 has no questions for any statement left uncovered.
  3. ENTITY 03

    Lesson

    Template
    templates/module.json.template
    Lands in
    content/modules/{certId}/{domainId}.json — the lessons[] array of one module file per domain.
    Validator catches
    no module file, duplicate lesson id, a missing title, eli5 or body, and a visualId that is not in the registry. It warns above 1600 body words, targeting 400–1200.
  4. ENTITY 04

    Question batch

    Template
    templates/questions.json.template
    Lands in
    content/questions/{certId}/{domainId}.part-N.json — one batch per file, in questions[]. The loader also accepts a plain {domainId}.json.
    Validator catches
    A certId/domainId that disagrees with the folder, an empty questions array, duplicate ids, fewer than three options, duplicate option ids, empty option text, a missing or unlisted correct answer, every option being correct, a whyWrong on a correct option, an explanation under 80 characters, and a difficulty outside 1, 2, 3. It warns above 40 questions in one file.
  5. ENTITY 05

    Flashcard deck

    Template
    templates/flashcards.json.template
    Lands in
    content/flashcards/{certId}/{domainId}.json — the cards[] array.
    Validator catches
    A card missing front or back, and a warning if the domain has no flashcard file at all. Card id uniqueness is not checked — the template asks for globally unique ids, so it is on you.
  6. ENTITY 06

    Interactive explainer

    Template
    templates/visual.tsx.template
    Lands in
    src/components/visuals/{visual-id}.tsx — default export, no props, all data in the file — plus a "{visual-id}" key in src/components/visuals/registry.ts.
    Validator catches
    Only the registry side: a lesson or question visualId that is not in the registry fails. The linter never reads the .tsx, so layout, hydration and accessibility are entirely on you — see the eight rules below.
  7. ENTITY 07

    Study plan

    Template
    None. scripts/scaffold.ts writes these inline, so there is no file in templates/ to keep in sync.
    Lands in
    content/study-plans.json — one object per plan, keyed {certId}-3-day, {certId}-7-day, {certId}-14-day. Each day holds blocks[] of kind: lesson, quiz, flashcards, mock, review or resource.
    Validator catches
    Nothing. The linter never opens study-plans.json, resources.json or insights.json. A malformed plan, a refId pointing at nothing, or a duplicate plan id all pass silently.

Checklist

The eight places a certification has to appear.

Tick each one. Six are written by pnpm scaffold:exam; two are yours alone. The badge on each row tells you which.

Also worth touching, though they change no behaviour: the prose mentions in README.md and CONTENT_SCHEMA.md. content/resources.json is deliberately not one of the eight — the scaffolder writes nothing there, because resources are only worth adding once the lesson they belong to exists.

The checklist that is already in every generated file

Eight rules for interactive explainers.

Read this before you touch the <svg>. Every rule below is a defect that actually shipped here and had to be fixed afterwards — the “why” is not theory, it is the post-mortem.

  1. Every <text> must fit inside the viewBox

    Measure the caption. If it is a full sentence, give it its own <tspan> line or wrap it. Do not eyeball it.

    Because an SVG clips silently. There is no scrollbar and no console warning when text runs past the viewBox — it just is not there. A caption that fitted when it was written overflowed the moment the wording changed. Two shipped that way and were invisible at every width, with nothing in the console to point at it.

  2. A clickable SVG node needs a keyboard-reachable <button> twin

    If a node in the diagram can be clicked, put a real <button> in the side panel that does the same thing, with the same state.

    Because <g onClick> is mouse-only. Two shipped this way: a tier selector and a stage selector that no keyboard user could reach at all. A mouse-driven diagram that looks complete is exactly how this hides.

  3. Use useHydratedReducedMotion, never useReducedMotion

    Import from @/lib/use-reduced-motion. Never from motion/react. Never Math.random() or Date.now() during render.

    Because motion's hook answers too early. useReducedMotion returns the true value on the very first client render while the server rendered false, so anything fed into an initial prop, a style object or a render branch produces markup that does not match the server HTML and React logs a hydration error. useHydratedReducedMotion is built on useSyncExternalStore with a false server snapshot, so both sides render false and the real preference is read after mount.

  4. Import cos and sin from @/lib/trig

    Never Math.cos or Math.sin in a visual. The rounded helpers make the server and browser bit-identical.

    Because V8 builds differ in the last bit. An SVG x or y attribute that differs between the two renders is a hydration mismatch, and the error names an attribute rather than the trigonometry that caused it.

  5. Colour through CSS variables only

    No hex literals anywhere in the file. Use the tokens: --ink, --ink-2, --muted, --surface, --surface-2, --bg, --line, --line-strong, --accent, --accent-strong, --accent-ink, --accent-text, --accent-soft, --good, --good-soft, --bad, --bad-soft, --info, --info-soft.

    Because the same diagram has to work in both themes. A hex literal is correct in exactly one of them. In SVG <text> set fonts with style={{ font: "600 15px var(--font-display)" }}, and keep --muted on --surface as the lightest pairing that still meets contrast.

  6. viewBox plus h-auto w-full, and nothing that can widen

    Never a fixed pixel width on the SVG. Panels holding text need min-w-0; grid tracks need minmax(0, 1fr).

    Because a long label widens the whole figure on a phone. A grid track defaults to a minimum of auto, which is the widest its content can get, so one long label pushes the diagram past the viewport instead of wrapping. This is the same failure as the role-picker badge on the marketing page.

  7. It has to read at 375px

    Side panels go in a grid that stacks on narrow screens. If one SVG genuinely cannot stack, give it a min-w, let the existing overflow-x-auto pan it, and say so in a comment.

    Because the diagram is the lesson. A lesson that is unreadable on a phone is not a lesson with a responsive problem, it is a lesson most readers do not finish.

  8. Every control is a labelled button, and the explanation is live

    Each control is a real <button> with an aria-label and aria-pressed. The current explanation sits in an aria-live="polite" region. The <svg> gets role="img" and an aria-label describing the current state, not a generic title.

    Because the Listen button reads that region's text aloud. Keep it one plain sentence per step. A bare “1/3” counter is what a screen reader stumbles over, so the number belongs in the visible label and the live region carries the sentence.

Two more habits that are not rules: user-driven motion only — no looping ambient animation, it fights reduced motion and it is the thing people find distracting while reading — and prefer user-driven steps, toggles and sliders. The reference implementation is src/components/visuals/agentic-loop.tsx.

Question writing

The bank is not a list of trivia.

Numbers below are computed across all 2,795 questions in content/questions/. The linter enforces the shape of a question; these are the judgement calls it cannot enforce for you.

a single batch, named for the domain it belongs to 
content/questions/{certId}/{domainId}.part-8.json

Shape

  • Difficulty mix. Across the bank: 535 easy, 1,408 medium, 852 hard — 19% / 50% / 31%. The house target is about 4 easy, 10 medium, 6 hard per twenty questions. 1 is recall of one documented behaviour, still scenario-framed; 2 is the standard case; 3 is competing real trade-offs, a subtle failure, or an anti-pattern that sounds correct.
  • Multi-select share. 717 of 2,795 are multi-select — 26%. Target 25–35%. Two entries in correct means “choose two”. The linter fails every option is correct, so this can never degenerate into a question with no distractor.
  • Four options, ids A to D. At least three, no duplicate ids, no empty text. Distractors are what a smart person says having missed exactly one key idea.
  • Batch size. 15 to 28 per file. The linter warns above 40.
  • Coverage. Every task statement in the domain needs questions, and fewer than three is a warning. foundations/d1-agentic carries 15 or 16 per statement across 106 questions.

Teaching material

  • Every non-correct option gets a whyWrong sentence. Forbidden on a correct option. The linter enforces both directions — but only on single-select questions. On multi-select it checks neither presence nor completeness, so the template's rule is the bar: every option you did not pick gets a sentence saying why it sounds right and is not.
  • explanation is 80 characters minimum and is a lesson, not a confirmation. Name the principle and the actual field or flag. The linter measures the length, so it will happily pass a useless one.
  • mindset is one line — the decision principle, phrased so a reader could reuse it. All 2,795 questions in the repo have one; the linter only warns when it is missing.
  • A scenario is concrete: a named organisation, real constraints, a real failure, two to four sentences. Reuse one rich scenario across a cluster of related questions, the way the real exam works. 1,375 of 2,795 questions carry one.
  • visualId on roughly 40–50% of a batch, only when a diagram genuinely explains why the answer is right. A decorative diagram teaches nothing and costs a lazy load.

The id convention, and why the batch marker matters

Ids look like ^[a-z]{1,2}-d\d+-[a-z0-9-]+$: cert prefix, domain number, batch marker, serial. In this repo that is f-d1-b1-001, f-d1-x3-014, v-d3-y4-001. The prefixes actually in use are f for foundations, p for professional, a for associate and v for developer — note that pnpm scaffold:exam derives its prefix from the first two characters of the --id instead, so rename the prefix after scaffolding to match the rest of that cert.

The linter warns on a malformed id but fails on a duplicate one, and then re-scans every question in the repository to fail with question id X also used in {file}. That second pass exists because the app's loader dedupes ids silently: collide and a question disappears from the bank with no error, no log and no gap you would notice. Use a fresh marker for every batch. The markers currently taken across all four certifications are b1 b2 b3 b4 b5 b6 b7, g1 g2 g3 g4 g5 g6, w6 w7 w9, x1 x2 x3 x4 x5, y4 y4b y5 y5b, z3 z4 z5 z6 z7.

Ground every technical claim in documented behaviour

Put one to three real URLs in sourceRefs, preferring platform.claude.com/docs/en/… and code.claude.com/docs/en/…, and reuse URLs already elsewhere in the bank rather than inventing them.

Never invent API behaviour. If you are not certain a claim is true of the Claude API, the Agent SDK or Claude Code, verify it first or write the question so correctness does not hinge on the uncertain detail. No “all of the above”, and do not repeat a question that already exists in the domain.

The loop

Verify in this order, and stop at the first gate.

Content first. It is fast, it catches the most, and nothing else matters if it fails.

the gate — nothing is finished until this is clean 
pnpm validate:content
  1. STEP 01 · CONTENT GATE
    Run pnpm validate:content
    Prints a question-bank table per domain — total, easy, medium, hard, multi-select, with a scenario — then any warnings, then problems. It exits non-zero only on problems; warnings are printed and it still passes. Fix every problem, and read the warnings: an id that does not match the convention and a task statement with two questions are both early signs of something real.
  2. STEP 02 · TYPES AND LINT
    pnpm typecheck and pnpm lint
    typecheck runs next typegen then tsc --noEmit; lint runs eslint. For a single explainer, the narrower commands are npx tsc --noEmit -p tsconfig.json and npx eslint src/components/visuals/<visual-id>.tsx — these are the exact commands scaffold:visual prints for you.
  3. STEP 03 · TESTS
    pnpm test
    vitest run. Relevant when you changed a loader or anything that resolves ids.
  4. STEP 04 · HYDRATION AND MOTION SWEEP
    Start the dev server, then run the sweep twice
    It signs in as the seeded QA user, opens one lesson per explainer, clicks up to eight controls inside each figure, and fails on any hydration error, any animation still running under reduced motion, or any element left stuck at opacity: 0. The dev server has to be on port 3111, which the script hard-codes.
    in one terminal 
    pnpm dev --port 3111
    in another — the second run forces reduced motion 
    node verify-hydration.mjs
node verify-hydration.mjs --rm
  • STEP 05 · EYES
    Look at it at 375px and 1280px, light and dark, reduced motion on
    Nothing in this repository checks that text fits inside an SVG, that a figure reads on a phone, or that a control is reachable by keyboard. Those three are the ones that shipped broken. This page is checked the same way: 390px and 1280px, both themes.

    • What the gate does not cover

    validate-content.ts reads certs.json, the module files, the flashcard files, the question files and registry.ts. That is all. It never opens resources.json, insights.json, study-plans.json, any .tsx file, or docs/index.html. It does not check that domain weights sum to 100, that flashcard ids are unique, that whyWrong is complete on multi-select questions, or that a registry key points at a file that exists.

    Passing the gate is necessary. It is not sufficient.

    Worked example

    One real domain, end to end.

    foundations/d1-agentic — “Agentic Architecture & Orchestration”, 27% of the exam, the largest single weighting in the repository. Every figure below was read out of the files listed.

    STEP 1The domain

    Declared once in content/certs.json, as an entry in the foundations cert's domains[]:

    content/certs.json 
    {
  "id": "d1-agentic",
  "name": "Agentic Architecture & Orchestration",
  "weight": 27,
  "color": "#C9772B",
  "taskStatements": [
    { "id": "1.1", "text": "Design and implement agentic loops for autonomous task execution" },

    The five foundations weights are 27, 18, 20, 20 and 15 — 100 exactly. Nothing enforces that; the developer exam's decimal weights add to 99.99999999999998 and the linter says nothing.

    STEP 2The lessons
